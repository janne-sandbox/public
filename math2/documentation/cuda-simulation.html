Chapter 02.5 · Development tooling

Run CUDA simulation without claiming a physical GPU.

Math2 provides a reproducible Docker installer for a pinned GPGPU-Sim and CUDA 11.7 development environment. It is an intermediate kernel-verification lane, not hardware release evidence.

Status boundary

The installer and smoke check are implemented. Exact Math2 CUDA kernels and simulator conformance are not implemented yet. A passing installation proves only that the compiler and simulator runtime were built from the pinned inputs.

Install

Requirements are Docker with network access and enough storage for multi-gigabyte CUDA layers. Run from any directory:

/path/to/math2/install-cuda-simulator.sh

The script builds math2-gpgpu-sim:cuda-11.7 from the digest-pinned upstream CI toolchain, checks out the pinned GPGPU-Sim revision, compiles it, and runs a smoke check for the expected revision, nvcc, and simulated libcudart.

Architecture and storage

Upstream images are linux/amd64. The installer selects that platform explicitly. Docker Desktop can emulate it on ARM hosts, but download, unpack, compile, and simulation are substantially slower. The pinned base image has roughly 5.5 GB of compressed layers; allow considerably more space after extraction and compilation.

Rebuild and overrides

# Ignore Docker build cache
./install-cuda-simulator.sh --no-cache

# Choose a local tag
MATH2_CUDA_SIMULATOR_IMAGE=sample-gpgpu-sim:dev \
  ./install-cuda-simulator.sh

# Inspect options without downloading
./install-cuda-simulator.sh --help

The platform, base image, and GPGPU-Sim commit also have environment overrides. Changing pins makes the result a different, locally selected environment; record those values with any evidence.

What simulation can verify

  • CUDA source compilation to PTX with the pinned toolkit.
  • Functional execution of supported PTX instructions through GPGPU-Sim.
  • Exact canonical output comparisons against the CPU reference once Math2 kernels exist.
  • Deterministic error and ordered-batch fixtures supported by the simulator.

What it cannot verify

  • The shipped JNI bridge against a production NVIDIA driver.
  • Physical allocation, synchronization, instruction, or device-failure behavior.
  • Performance, transfer cost, or suitability thresholds on release hardware.
  • The mandatory CUDA hardware conformance gate.

Troubleshooting and cleanup

If an ARM-host pull repeatedly stalls, use an AMD64 CI runner with the pinned image pre-cached. Docker retains successfully built images; remove the local image only when its cache is no longer needed:

docker image rm math2-gpgpu-sim:cuda-11.7

Do not use broad Docker pruning commands: other projects may share the same Docker daemon and caches.
